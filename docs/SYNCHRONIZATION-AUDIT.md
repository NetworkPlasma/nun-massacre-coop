# Nun Massacre synchronization audit

Audit target: the local **Nun Massacre Definitive Edition (Windows) 2022.06.08** managed assembly. Evidence is the locally decompiled code in `.research/game`. This document describes code surfaces and requirements; it is **not a statement that the multiplayer implementation supports or has tested every row**. Scene assets, serialized UnityEvent listeners, and NodeCanvas graphs contain additional gameplay that cannot be exhaustively established from C# classes alone. The assembly also contains older and apparently reused game systems; existence of a class is not proof that every scene uses it.

## Confirmed integration anchors

- `GrannyClone.pReferences` links the first-person player to `FirstPersonController`, `fpsHealth`, `PlayerStates`, `Inventory`, and `InteractionSystem`.
- `DifficultyController` links the Nun to **`Humanoid.Motor2d` and `NodeCanvas.StateMachines.FSMOwner`**. Its `SetDifficulty` changes movement, damage multipliers, world objects, lighting, ammunition, and the Nun graph's `sightDelay` / `sightDelay_Light`; it sends `StartDelay` or `Go Away Forever` to that graph. This is a stronger integration anchor than guessing from class names.
- `NunController` controls Nun audio volume, jumpscare settings, and static effects. It is **not** the Nun's AI controller.
- `GrannyClone.Tasks.SavePlayerReference.OnExecute` stores the first object tagged `Player` and `Camera.main` into graph parameters. Several other tasks cache player crouching, vent, and hiding state through static events. These references must be made player-aware for the Nun to pursue remote players correctly.
- `MessagesGranny` is a set of static delegates without a player identifier. Creating multiple copies of original local player controllers in one process will cross-wire input, inventory, health, camera, and interaction messages. Remote visual bodies should not subscribe as another local player.

## Safe implementation rules supported by this audit

1. **Identify the scene object before binding it.** Static paths need scene identity, sibling indices and component identity. Paths/names alone are fragile after random parenting and inventory reparenting. Assign IDs before those mutations and send a manifest/hash; dynamic spawns need host-assigned IDs and spawn records.
2. **Do not build a network-accessible general reflection RPC.** Use a fixed command table with typed arguments, limits, ownership, range checks, scene epoch and monotonically increasing request IDs. A peer must not select arbitrary component methods, instantiate arbitrary assets or load arbitrary scenes.
3. **Patch semantic boundaries, with replay guards.** Harmony postfixes on completed host mutations are useful observation points. Client prefixes can turn approved actions into host requests. A nested execution/replay guard is necessary because `Interact -> StateChange -> UnityEvent -> Place -> ClearEquippedItem` is one transaction, not five unrelated actions.
4. **Separate state restoration from event replay.** `StateSetNoEvent` is useful for restoring the index, but does not reproduce world effects from prior states. Late join needs persistent results (doors, item placement, active objects, gas, broken glass, spawned traps) as well as indices. Restoring raw fields alone does not execute dependent logic; blindly replaying `StateChange` can execute it twice.
5. **Retain one original local player per process.** Remote avatars should have explicit renderers/physics proxies and player records, rather than complete copies of single-player components subscribed to static delegates. Host command execution must supply actor inventory/camera/position context deliberately.
6. **Reconcile random results, not just random seeds.** `RandomActivate` has a separate clock-seeded generator. Local footsteps, gun shake, shards and other cosmetic effects use Unity RNG. Initial object identity/placement/active-state snapshot must be authoritative after startup.
7. **Suppress specific client simulation.** World physics, enemy AI, shared randomization and shared hazard timers cannot continue freely while applying host transforms. Conversely, disabling every `FSMOwner`, `MonoBehaviour`, collider, or animator breaks puzzles, UI and individual player behavior.
8. **Keep host and local-player clocks distinct.** Menus/cutscenes must not inadvertently pause network polling or the shared simulation. Use unscaled time for connection management and restore modified time scale on leave. `Global.Manager.FreezeTime` and `PlayerStates.Menu_Exit` write `Time.timeScale`.

## Evidence still required before “full synchronization” can be claimed

- Runtime scene object/component inventory and all active Nun FSM graph/blackboard tasks.
- Serialized UnityEvent listener inventory for every interactable state, pickup, puzzle, death, respawn and ending.
- Each playable scene/mode, difficulty, randomization configuration, and all ending routes.
- At least two real game instances exercising simultaneous contested pickup, remote item use, doors/dragging, enemy detection/attack of each player, death/respawn, hiding, vents/gas, traps, firearm/throwable impacts, puzzle completion and scene transition.
- Late join after mutations; rejoin and disconnect while holding an item, dragging a door, trapped or in a cutscene; host disconnect; packet delay/loss; connection rejection for mismatched game/mod build.
- Verify object identities stay matched after random placement and inventory movement, and failed commands cannot mutate other players' inventory or world state.

Until those checks pass, the honest status is an implementation under development, not verified feature-complete multiplayer.
